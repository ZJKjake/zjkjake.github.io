## The problem

If you use more than one AI coding tool, you have no idea how much quota you have left. Cursor
shows usage on a web dashboard. Claude Code reports limits through a status-line JSON contract.
Codex exposes rate-limit windows through a local app-server. None of them tell you anything in
the editor, which is where you are when the limit matters. You find out you are rate-limited by
being rate-limited, usually mid-task.

The obvious version of this extension is a status bar item with a single percentage in it. I
built that first and threw it away, because a single percentage is a lie.

## Why one number is wrong

The three providers do not meter the same thing. Claude Code has a five-hour window and a
seven-day window, which are independent — you can be fine on one and exhausted on the other.
Codex reports a general rate limit with its own windows, plus model-specific limits underneath
it. Cursor reports plan usage on a different basis entirely.

There is no defensible way to average those into one score. Any weighting you pick is made up,
and the resulting number is confidently wrong in exactly the situation the user cares about.
So AgentMeter never combines unrelated provider limits. The status bar shows them side by side,
and the hover tooltip expands each provider into the windows it actually meters:

```text
AgentMeter · Cursor 70% · Claude Code — · Codex 47%

  Cursor
  Other Models pool · 70% left · resets in 8d
  Cursor Models pool · 99% left · resets in 8d

  Claude Code
  Setup required · Run AgentMeter: Configure Claude Code to show usage.

  Codex
  1-week window · 47% left · resets in 4d
```

That output is generated by running the real formatter against a fixture, not mocked up for
this page. Two things in it are the whole design. Cursor gets two bars because it meters two
pools, and averaging them to "84%" would hide that one is nearly exhausted. Claude Code shows
an em dash rather than a number, because the extension has not been configured to read it —
and the tooltip says which command fixes that.

The footer line in that screenshot — "Percentages always mean remaining quota and are never
combined. Credentials stay with each provider." — is in the UI itself, because a user should
not have to read a case study to know what a number on their screen means.

Two smaller decisions came out of the same principle. Everything is displayed as **remaining**
percentage rather than used, because remaining is the number you act on — `remaining = 100 −
used`, applied once at the boundary so the status bar, sidebar, tooltips, and detail views can
never disagree. And a fresh install shows no usage at all. Plenty of extensions ship with
plausible sample data in the UI, which means a new user cannot distinguish "you have 80% left"
from "we have not loaded anything yet."

## Making unavailability a first-class state

This is the part I would defend in a design review. Every provider integration can fail in
several distinguishable ways, and collapsing them into one error state throws away the only
information the user needs — namely, whether there is something they can do about it.

A provider in AgentMeter is always in exactly one of: `Connected`, `Setup required`,
`Sign-in required`, `Unsupported`, `Unavailable`, `Stale data`, or `Mock/development data`.
Those are different problems with different fixes. "Sign-in required" means go authenticate.
"Unsupported" means stop waiting, this will not work on your plan. "Stale data" means the
number on screen is real but old.

And when a value genuinely is not known, the UI shows `—`. Not `0%`, not a spinner that never
resolves, not a guess. A zero in a quota meter reads as "you are out," which is the opposite of
"I could not check."

<Callout label="Design constraint">
  AgentMeter is local-first and reads provider state read-only. It owns no credentials —
  authentication stays with each provider's own CLI. The Cursor adapter is disabled by default
  and marked experimental, because Cursor does not publish a stable personal usage API and I
  did not want a default-on integration that silently breaks when an internal endpoint changes.
</Callout>

## Architecture

The source is about 4,500 lines of TypeScript in four layers, and the layering is enforced by
direction of imports rather than by convention:

- **`domain/`** — what usage *is*. The quota and provider types, the normalisation rules, and
  the registry of which tools exist. No I/O and no VS Code API — it describes providers without
  knowing how to reach any of them.
- **`application/`** — the usage service, the refresh scheduler, and the dashboard store. This
  is where "refresh every five minutes, and also whenever the editor regains focus" lives.
- **`infrastructure/`** — one collector per provider, each responsible for the specific
  indignity of getting data out of that provider, plus a Claude status-line bridge that
  sanitises the official JSON contract into a local cache. There is a mock collector alongside
  the real ones.
- **`presentation/`** — the status bar formatter and manager, and the sidebar webview.

The payoff is that the interesting logic is testable without an editor. Because `domain` and
`application` have no VS Code dependency and every provider sits behind a collector interface,
the mock collector is not a testing hack — it is another implementation of the same interface.
That is what makes 83 tests possible in a codebase this size.

The tests concentrate exactly where the bugs are: 13 on the status bar formatter, 13 on webview
content, 11 on the usage service, 10 each on the Claude and Codex collectors, 7 on the Cursor
adapter. The formatter has the most because it has the most edge cases — missing values,
multiple windows, long provider names, and the difference between zero and unknown.

## Four bugs that all looked fine

The `0.1.3` release fixed four display bugs. What makes them worth writing about is that none of
them threw an error, and all four rendered something a user would have believed.

**Every progress bar was full.** The webview sets bar widths from a percentage, and it did that
the obvious way — `style="width: 34%"` in the markup. The webview's content security policy
names a nonce for styles, which blocks inline style attributes. So the width never applied and
every bar fell back to its default full width, on a dashboard whose entire job is showing you
how much is left. The numbers beside the bars were correct the whole time, which is exactly why
it survived a release. The fix was setting widths through the CSSOM with the data carried on
`data-` attributes. The preview script now deliberately keeps the real CSP, because stripping
it is what hid this in the first place.

**The Codex number flickered between two correct values.** The compact status bar reading
alternated on refresh. Both values it alternated between were real quotas — the headline picker
was selecting whichever the provider happened to return first, and the order was not stable.
Fixed by defining the headline as *the quota closest to running out*, which is the one you
needed to see anyway. Response order is not a ranking, and I had been treating it as one.

**Two rows had the same name.** Codex exposes more than one quota that is legitimately a
one-week window, so the sidebar rendered two bars both labelled "1-week window" with different
values. Reasonable to read as a bug in the extension. Fixed by labelling the pool rather than
the period.

**Cursor's roll-up became a phantom third bar.** Cursor's API returns a `totalPercentUsed`
alongside the individual pools. I rendered it, so it appeared as a third quota — but it is a
summary of the two bars sitting directly above it, and showing it made the user's total look
like it had three components. Dropping it is the same rule as never averaging providers,
applied one level down.

## Shipping it

CI runs on every push and pull request: type-check, then the full test suite, then package the
VSIX. Packaging in CI matters more than it sounds — a build that type-checks and tests clean can
still fail to package because of a manifest problem, and finding that out at publish time is
how you end up shipping a broken release. There are tests for the manifest and for the Open VSX
publish path for the same reason.

Four versions are published, `0.1.0` through `0.1.3`. As of September 2026 it has **1,410
downloads** on Open VSX, which I checked against the registry API rather than trusting the
number on the listing page. GitHub stars are zero; downloads are the metric that means
anything here, and they come from the registry, not from GitHub.
